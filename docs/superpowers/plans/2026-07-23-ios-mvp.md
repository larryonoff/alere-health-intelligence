# Alere iOS MVP — Implementation Plan

Date: 2026-07-23  
Design: `docs/superpowers/specs/2026-07-23-ios-mvp-design.md`

## Objective

Build a small native iOS application that validates Alere's core loop:

> goal → conversation → one action → feedback → weekly synthesis

The implementation must preserve `skill/SKILL.md` as product-independent
assistant behavior and keep all interface, persistence, model-provider, and iOS
integration concerns outside the skill.

## Delivery strategy

Build one complete vertical slice before adding secondary system entry points.
Every phase ends in a runnable application or deterministic tests. Avoid empty
future-facing modules.

## Phase 1 — Project foundation

### Tasks

1. Create an Xcode workspace and thin iOS application target under `App/iOS`.
2. Create the root local Swift package and one `AppFeature` library product.
3. Add the initial modules:
   - `AppFeature`;
   - `OnboardingFeature`;
   - `AssistantFeature`;
   - `Model`;
   - `AssistantClient`;
   - `Resources`;
   - `SharedUI`.
4. Add matching test targets.
5. Configure Swift 6 strict concurrency and main-actor defaults for UI targets.
6. Add only the initial dependencies:
   - TCA;
   - `swift-dependencies`;
   - `sqlite-data`;
   - `swift-tagged`.
7. Configure SwiftGen for English and Russian localization.
8. Add a minimal application scene that launches `AppFeature`.

### Acceptance criteria

- The workspace opens and resolves dependencies.
- The real iOS scheme builds for a simulator.
- The package dependency graph contains no feature cycles.
- English and Russian generated localization accessors compile.
- A smoke test launches the root feature.

## Phase 2 — Local model and persistence

### Tasks

1. Define strongly typed identifiers and records for:
   - profile;
   - primary goal;
   - conversation;
   - message;
   - proposed and confirmed action;
   - action feedback;
   - proposed and confirmed memory;
   - weekly synthesis.
2. Define schema migrations and database bootstrap.
3. Implement queries for:
   - current goal;
   - active conversation;
   - recent context;
   - active action;
   - pending memory proposals;
   - weekly history.
4. Implement deletion of individual memories and all local user data.
5. Keep AI-provider payloads out of persisted domain records.

### Acceptance criteria

- A fresh database boots successfully.
- Migrations are deterministic and covered by tests.
- Relaunch restores confirmed data.
- Rejected memory is not persisted.
- Full local deletion leaves no user conversation or profile records.

## Phase 3 — Goal onboarding

### Tasks

1. Implement one short onboarding screen.
2. Offer four suggested goals, a custom goal, and “not sure yet”.
3. Make selection optional and editable.
4. Persist only the confirmed goal.
5. Route directly to the assistant after completion or skip.
6. Add accessible labels, Dynamic Type layouts, and localized copy.

### Acceptance criteria

- The user can complete onboarding in one decision.
- Skipping does not reduce access to the assistant.
- A custom goal supports realistic long text.
- Returning users do not see onboarding again unless local data is reset.
- Reducer tests cover select, customize, skip, save, and retry states.

## Phase 4 — Assistant client contract

### Tasks

1. Define a provider-independent `AssistantClient`.
2. Define structured request context containing only:
   - current goal;
   - confirmed memories;
   - bounded recent conversation;
   - active action and feedback;
   - current user message.
3. Define structured output containing:
   - response text;
   - one optional proposed action;
   - optional memory proposals;
   - source or evidence metadata;
   - safety route;
   - uncertainty metadata.
4. Implement deterministic test and preview clients.
5. Implement timeout, cancellation, offline, and retry semantics.
6. Convert `skill/SKILL.md` into runtime instructions without adding
   application-specific behavior to the skill itself.
7. Add deterministic fixtures for food choice, comparable product review,
   recipe adaptation, meal planning, shopping, storage, and habit support.

### Acceptance criteria

- Feature modules do not import a concrete AI SDK.
- Responses cannot contain more than one active proposed action.
- Memory proposals cannot become confirmed without a user action.
- Cancellation does not append a partial persisted assistant response.
- Contract fixtures cover normal, uncertain, high-risk, and failure cases.
- Fixtures verify metric units, Polish złoty, and realistic Polish availability
  when regional context is present.

## Phase 5 — Text conversation vertical slice

### Tasks

1. Build the single main assistant screen.
2. Add:
   - current goal/focus;
   - contextual starter prompts;
   - conversation timeline;
   - text composer;
   - sending, streaming or waiting state;
   - retry state.
3. Connect the feature to persistence and the deterministic assistant client.
4. Preserve draft text when a request fails.
5. Persist completed message pairs.
6. Render evidence and safety information without overwhelming the primary
   response.

### Acceptance criteria

- A user can send a message and receive a response.
- A failed request retains input and offers retry.
- Relaunch restores the conversation.
- Starter prompts populate the composer or start a clearly visible request.
- The interface works without a tab bar.
- VoiceOver and AX5 Dynamic Type can reach the complete core loop.

## Phase 6 — Action and approved memory

### Tasks

1. Present at most one proposed action beneath the relevant response.
2. Support accept, edit, and decline.
3. Add later feedback: attempted/not attempted and useful/not useful.
4. Present proposed memories independently from assistant prose.
5. Support confirm, edit, reject, inspect, and delete.
6. Feed only confirmed information into subsequent requests.

### Acceptance criteria

- Declining an action or memory changes no durable personal context.
- Editing shows the exact value that will be saved.
- Only one action can be active.
- Feedback is reflected in the next assistant request.
- Users can inspect and delete every saved memory.

## Phase 7 — Weekly synthesis

### Tasks

1. Define the seven-day observation window and eligibility rules.
2. Generate a synthesis from confirmed interactions and feedback.
3. Present:
   - what is working;
   - one pattern;
   - one next focus;
   - uncertainty.
4. Provide an honest insufficient-history state.
5. Store generated summaries so changes are auditable to the user.

### Acceptance criteria

- Sparse history never produces false completeness.
- The synthesis contains only one next focus.
- A user can open the latest summary from the main screen.
- Tests cover sufficient, sparse, empty, and high-risk histories.

## Phase 8 — Voice input

### Tasks

1. Add a speech-transcription dependency boundary.
2. Implement native speech capture and transcription.
3. Put transcribed text into the same editable composer used for typing.
4. Handle microphone permission denial and transcription failure.
5. Do not store raw audio after transcription.

### Acceptance criteria

- Voice input never bypasses text review before sending.
- Denied permission leaves the text experience fully usable.
- Cancellation stops capture and discards temporary audio.
- The feature has deterministic permission and transcription tests.

## Phase 9 — Foundation Models and fallback

### Tasks

1. Implement the on-device adapter for supported Foundation Models operations.
2. Check model and locale availability before selection.
3. Implement one server fallback adapter.
4. Centralize routing inside `AssistantClient`.
5. Minimize server context and disclose network processing in privacy copy.
6. Validate both adapters against the same structured contract fixtures.

### Acceptance criteria

- Features cannot observe or depend on which provider answered.
- Unsupported devices and locales use fallback without crashing.
- Missing server configuration produces a recoverable error.
- Safety fixtures pass through both adapters.
- Provider changes do not alter persisted domain schemas.

## Phase 10 — App Intents

### Tasks

1. Add the extension-safe `AppIntents` module.
2. Implement intents for:
   - ask Alere;
   - help choose food;
   - open the latest weekly synthesis.
3. Provide App Shortcuts phrases and localized titles.
4. Make suitable intents available to Siri, Shortcuts, the Action Button, and
   Control Center where the platform supports them.
5. Route intents into the existing assistant flow rather than duplicating
   business logic.

### Acceptance criteria

- Each intent opens or invokes the same domain workflow as the app.
- No database or AI implementation is duplicated in the intents module.
- Intent cancellation and unavailable-model states are recoverable.
- Shortcut titles and phrases work in supported localizations.

## Phase 11 — Safety, privacy, and quality

### Tasks

1. Add versioned evaluation fixtures for:
   - ordinary food choices;
   - incomplete weekly histories;
   - allergies;
   - pregnancy and children;
   - eating-disorder signals;
   - medication interactions;
   - symptoms and chronic disease;
   - requests to stop treatment.
2. Review source metadata and uncertainty rendering.
3. Verify local-data deletion and server-context minimization.
4. Test accessibility:
   - VoiceOver;
   - AX5 Dynamic Type;
   - Reduce Motion;
   - Increase Contrast;
   - 44-point touch targets.
5. Run the complete deterministic test suite and real iOS simulator build.
6. Conduct a small hands-on usability session using realistic conversations.

### Acceptance criteria

- Every predefined higher-risk case follows the required safety route.
- No evaluated recommendation contradicts its cited source.
- The complete core loop is usable with VoiceOver.
- All deterministic tests pass.
- The real application scheme builds successfully.
- Known model-quality limitations are recorded separately from code defects.

## Deferred backlog

Do not begin these items during the MVP implementation:

- photo capture or food-image analysis;
- Share Sheet;
- HealthKit;
- widgets;
- Live Activities;
- barcode and nutrition databases;
- exact calorie tracking;
- CloudKit;
- user accounts;
- analytics and monetization;
- Apple Watch;
- Android.

## Final acceptance scenario

On a clean installation:

1. The user selects or skips one goal.
2. The user starts from a suggested prompt or writes a question.
3. Alere answers and proposes no more than one practical action.
4. The user accepts, edits, or declines the action.
5. Alere proposes memory only with explicit confirmation.
6. The user later reports whether the action was attempted and useful.
7. After sufficient interactions, Alere produces an appropriately uncertain
   weekly synthesis.
8. The user can reach core entry points through App Intents.
9. The user can inspect and delete saved memory and all local data.
